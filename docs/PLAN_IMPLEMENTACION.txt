PLAN DE IMPLEMENTACION - AETHER ITSM
Ultima actualizacion: ver historial de git de este archivo.

Como usar este documento
-------------------------
Las fases estan en orden de cascada: cada una depende de que la anterior
exista, no solo de que "tenga sentido" hacerla antes. No saltar una fase
sin haber marcado sus items como hechos, o la siguiente se construye sobre
algo que no esta ahi todavia.

Cada item tiene: que es, por que va en ese orden (de que depende), y que
archivos toca aproximadamente. Se implementa de a uno, y se marca [DONE]
al terminar.

FASE 5 - ENDPOINT DE CHAT SINCRONO
-----------------------------------------------------------
La pieza mas grande del roadmap nuevo. Depende de Fase 2 (necesita tools
reales para poder responder "el servidor esta caido" o crear un issue en
el mismo turno) y se beneficia de Fase 3 y 4 ya existiendo, pero puede
arrancarse con un triage mas simple si se prioriza esto primero.

5.1 [ ] Decidir el modelo de conversacion: un thread_id por conversacion de
        chat (no por ticket_id de ITSM) - probablemente uno por usuario
        activo, persistido igual que los threads de ticket via el mismo
        checkpointer.
5.2 [ ] Nodo de triage ligero ("Concierge"): intenta responder directo con
        RAG + las tools de las Fases 3/4 ANTES de escalar al Supervisor
        pesado de riesgo 0-4. La mayoria de "no me deja entrar" deberian
        resolverse aca sin generar un Ticket formal.
5.3 [ ] Definir el criterio de "esto si necesita convertirse en Ticket": si
        el Concierge no puede resolverlo en 1-2 turnos, ahi si se crea un
        Ticket real y se sigue el flujo ya existente (Supervisor -> Policy
        -> Execution/Draft Plan).
5.4 [ ] Nuevo endpoint POST /api/chat: auth por cookie de sesion normal (el
        empleado ya logueado), no por x-api-key de webhook. Devuelve la
        respuesta del turno actual (sincrono esta bien para el MVP;
        streaming es una mejora posterior, no un requisito).
5.5 [ ] Historial de conversacion: decidir si vive solo en el checkpointer
        de LangGraph o si tambien se persiste en SQL para poder mostrarlo
        en el dashboard de admin.


FASE 6 - BUSQUEDA DE CODIGO ON-DEMAND EN GITHUB
-----------------------------------------------------------
Depende de Fase 5 (el chat es el consumidor natural de esto) y de tener
un github_token con scope de lectura de codigo ya configurado (Fase 0,
onboarding). Deliberadamente NO se propone indexar todo el repo en
pgvector: el chunking de texto plano no funciona bien para codigo, y un
indice pre-calculado se desactualiza. Mas simple y mas preciso: una tool
que busca on-demand cuando el agente la necesita.

6.1 [ ] Tool nueva: search_github_code(repo, token, query) usando la API
        de busqueda de codigo de GitHub.
6.2 [ ] Logica/prompt para que el agente decida cuando vale la pena usar
        esta tool (preguntas que mencionan algo especifico del proyecto,
        no problemas genericos de "la VPN no conecta").
6.3 [ ] Documentar limitaciones: rate limits de la API de busqueda de
        GitHub, y que el token necesita el scope correcto si el repo es
        privado.
