PLAN DE IMPLEMENTACION - AETHER ITSM
Ultima actualizacion: ver historial de git de este archivo.

Como usar este documento
-------------------------
Las fases estan en orden de cascada: cada una depende de que la anterior
exista, no solo de que "tenga sentido" hacerla antes. No saltar una fase
sin haber marcado sus items como hechos, o la siguiente se construye sobre
algo que no esta ahi todavia.

Cada item tiene: que es, por que va en ese orden (de que depende), y que
archivos toca aproximadamente. Se implementa de a uno, y se marca [DONE]
al terminar.

FASE 6 - BUSQUEDA DE CODIGO ON-DEMAND EN GITHUB
-----------------------------------------------------------
Depende de Fase 5 (el chat es el consumidor natural de esto) y de tener
un github_token con scope de lectura de codigo ya configurado (Fase 0,
onboarding). Deliberadamente NO se propone indexar todo el repo en
pgvector: el chunking de texto plano no funciona bien para codigo, y un
indice pre-calculado se desactualiza. Mas simple y mas preciso: una tool
que busca on-demand cuando el agente la necesita.

6.1 [DONE] search_code(repo, token, query) en src/integrations/github.py.
        DESVIACION DELIBERADA del texto original de este item: NO es una
        tool MCP que el LLM invoque con tool_name/tool_args. Una tool MCP
        expone sus parametros declarados tal cual en el prompt (ver
        mcp_client.prompt_catalog()), lo que hubiera significado pedirle al
        LLM que "complete" repo/token el mismo, exactamente el problema que
        Fase 3 ya evito para la creacion de issues. concierge.py obtiene y
        desencripta el token del tenant server-side y solo la query llega
        al contexto del LLM.
6.2 [DONE] Heuristica regex (_CODE_QUESTION_PATTERN en concierge.py) sobre
        el mensaje del usuario decide cuando vale la pena buscar codigo,
        antes de la unica llamada al LLM del turno (evita una segunda
        vuelta de LLM solo para decidir si buscar).
6.3 [DONE] Limitaciones documentadas en el docstring de search_code(): rate
        limit de la API de busqueda de codigo de GitHub (10 req/min
        autenticado) y que el repo privado necesita un token con scope de
        lectura de codigo - no hay retry/backoff implementado, una falla
        simplemente omite el contexto de codigo sin bloquear el turno.
